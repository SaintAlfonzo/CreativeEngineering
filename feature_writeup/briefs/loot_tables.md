## Shared: framework extensions (`05_tuning.js`)

Used by #1, #2, #5, #6, #11, #12. Not a TODO row of its own; build it with the first row that needs it.

### Now
- `L.alias(missing, [pools])` (05_tuning.js line 539) already creates a table from pools, as `minecraft:chest`, and only
  if no source ships the id (`plan()` line 631, `rewriteTable` line 1141). It is the "define" primitive under another
  name; items in its pools are put into the index (`linkPools`, line 617), so packing and tuning reach them.
- `L.add` (line 488, applied in `addItems` line 844) adds only `minecraft:item` entries (`itemEntry`, line 777) and
  rejects anything `Item.exists` doesn't know. No way to add a `minecraft:loot_table` entry at a share, to replace a
  table's pools, or to swap one kind of entry for another.

### Build
1. `L.define(id, pools)`: alias with pools, but with a clear name and a guard that the id is in the pack's own
   namespace (`creativeengineering:loot/...`). Implementation: `T.alias(id, pools)` plus a `T.defined[id] = true` set
   for `/loottuning` and the sim.
2. `L.addRef(tables, tableId, { share | weight, pool, except, conditions })`: same planning and share math as `L.add`;
   the new entry is `{ type: 'minecraft:loot_table', name: tableId }`. In `plan()`, call `link(table, tableId)` for each
   hit (line 608) so post-roll reach is right. In `addItems`, branch on `ad.ref`: skip the `Item.exists` /
   `itemsIn(entries)[...]` duplicate check, skip when the pool already has a `loot_table` entry with that name.
   Sketch:
   ```js
   T.addRef = function (tables, ref, opts) {
       opts = opts || {}
       // same share / weight validation as T.add
       T.adds.push({ tables: matchers(tables, 'addRef tables'), except: matchers(opts.except, 'addRef except'),
           ref: normId(ref), item: null, share: opts.share, weight: opts.weight,
           pool: opts.pool === undefined ? null : opts.pool, conditions: opts.conditions || null })
   }
   // addItems: var ne = ad.ref ? refEntry(ad.ref, ad.conditions) : itemEntry(...)
   ```
3. `L.replaceEntries(tables, test, ref)`: in each matching table, every entry for which `test(entry)` is true (raw
   JSON) becomes `{ type: 'minecraft:loot_table', name: ref, weight: <same>, quality: <same>, conditions: <same> }`.
   Runs right after `addItems` (before packing and tuning). `test` gets the entry JSON, so #11 can match
   `name == minecraft:book` + an `enchant_randomly` function with no `enchantments` list. Count replacements in
   `T.stats`.
4. `L.remap(table, pools | ref)`: replace a table's pools (like `useVanilla`, step 2 of `rewriteTable` line 1149) with
   the given pools or one roll of `ref`. Keep the declared type from the index. Needed by #1 / #2 only.
5. `/loottuning` and the `[loot-tuning]` log line: add `defined`, `refs added`, `entries replaced`, `remapped`.
6. `tools/loot_tuning_sim.js`: the sim runs the real 05 + 07, so the new calls run there too; add checks: every
   `addRef` / `replaceEntries` target names a table that exists (jar, alias or define), no defined table is empty,
   and (#10 / #11) no table has a `minecraft:book` entry with an unrestricted `enchant_randomly` left.
7. Document the calls in the header of `07_rules.js` (lines 8-18), in `loot/README.md` ("Script rules" table) and in
   loot.md 3.8.

### Gotchas
- Tables created by `define` only exist if the pre-roll pass is active (`settings.enabled`); with the kill switch off
  every `addRef` would point at a missing table and roll nothing (no crash, Minecraft logs it). Acceptable; note it in
  LT-10.
- A `loot_table` entry hides the items from JER's per-table view only partly (JER follows references) and from the
  catalog's `where`; the generator's index sees them through `loot_runtime_additions.json` only if `writeAdditions`
  records refs. Record them.
- `addItems` skips pools that `needsFallback` (composite / `expand` tag pools); the same applies to `addRef`.

### Build
1. Tier tables with `L.define` (Shared step 1), in a new block of 07_rules.js:
   - `creativeengineering:loot/books/basic`: one pool, one entry per allowed enchantment: `minecraft:book` +
     `set_enchantments {<id>: 1}`, weight by vanilla rarity (common 10, uncommon 5, rare 2, very rare 1). Contents:
     vanilla non-treasure, non-curse + vanilla-like mod ones (user: Domestication Innovation; recommend also

     level.
   - `.../books/high` (to define): e.g. `enchant_with_levels 20-39, treasure: true` is NOT safe (unfiltered registry);
     use an explicit list of treasure enchantments (mending, frost_walker, soul_speed, swift_sneak) + intermediate.
2. Replace entries (Shared step 3):
   ```js
   function bookWith(fnTest) {
       return function (e) {
           if ((e.type || 'minecraft:item').replace('minecraft:', '') !== 'item') return false
           if (e.name !== 'minecraft:book' && e.name !== 'book') return false
           return (e.functions || []).some(fnTest)
       }
   }
   var randomAny = function (f) { return /enchant_randomly$/.test(f.function) && !(f.enchantments && f.enchantments.length) }
   var levels = function (f) { return /enchant_with_levels$/.test(f.function) }
   L.replaceEntries(/./, bookWith(randomAny), BOOKS_BASIC)
   L.replaceEntries(/./, bookWith(function (f) { return levels(f) && !f.treasure }), BOOKS_INTERMEDIATE)
   L.replaceEntries(/./, bookWith(function (f) { return levels(f) && f.treasure }), BOOKS_HIGH)
   ```
   Leave explicit-list entries alone (curated by their mod), except DI's pet shop (its own).
3. Tools, weapons and armor with `enchant_randomly` / `enchant_with_levels` are out of scope (their item filters keep
   NEA and pet enchantments off them).
4. Sim check (Shared step 6): no unrestricted book entry left; count replacements per tier.

### Ids and data
- Table ids `creativeengineering:loot/books/{basic,intermediate,high}` (new). Vanilla enchantment ids (1.19.2).

- **Domestication Innovation's book injects** (`config/domestication-innovation.toml` `[loot]`, chances 0.15-0.65):
  keep, they're the mod's own source of pet books.

### Gotchas

## tables #1: Comprehensive loot table system
Status Planned / Work KubeJS / data / `loot/tables #1`

### Goal
Remap every container table into a tree of shared tables (`container/village/leatherworker/mediocre`,
`.../treasure`, `container/ocean/shipwreck/treasure`...), each item defined once and pulled in by many leaves,
reusing existing tables where they fit. Draft contents: loot.md 7 "Loot table changes" (basic: mob, crafting,
minable, emeralds, tools, food, building, rare random; blacksmith / armorer).

### Now
- 290 roots / 405 container tables (catalog); 3,874 template containers. Per structure, which tables:
  [by_structure.md](../loot_catalog/by_structure.md); per table, every entry: `loot_catalog/tables/<ns>.md`.
- The framework rewrites tables but has no "replace this table's pools" or "new table" call beyond `alias` /
  `useVanilla` (Shared).

### Build
1. Shared extensions (`define`, `addRef`, `remap`).
2. **Tree file**: `kubejs/server_scripts/loot/loot_tree.json` (read like `loot_config.json`, `readJson` in 05_tuning.js
   line 139): `nodes` (id -> pools, entries naming `global.item` **keys**, resolved at load, so ids stay in the dict)
   and `map` (container table -> node). A new `09_tree.js` (priority 0, after 07) calls `L.define` per node and
   `L.remap(table, node)` per mapped table. Unmapped tables stay as they are, so it can be rolled out family by family.
3. **Category nodes first** (loot.md 7 drafts): `container/basic/{mob,crafting,minable,emeralds,tools,food,building,rare}`,
   tier wrappers `.../mediocre`, `.../treasure` (more rolls, rarer pools), profession nodes
   (`container/village/blacksmith`, `.../leatherworker`...), each a few `loot_table` refs + its own items. Rows #5, #6,
   #11, #12's tables slot in as nodes (`creativeengineering:loot/cans/basic` -> `container/basic/food/cans`, or keep
   the ids and reference them).
4. **Generator** `tools/gen_loot_tree.py`: drafts `map` from the index + catalog by id heuristics (profession word in the
   id, `village`, `outpost`, `shipwreck`, `dungeon`, `library`...), prints unmapped tables; the user edits the result.
5. **Roll-out order:** vanilla villages (16) -> Terralith / T&T / Sky Villages / SimplyHouses houses -> dungeons and
   underground -> ocean -> the rest. After each, `node tools/loot_tuning_sim.js`, `/reload`, a few `/loot give`.
6. Code-injected pools (Supplementaries, Botania, Sophisticated Backpacks...) still get appended by Forge to vanilla
   tables after the remap (the KubeJS edit doesn't block `LootTableLoadEvent`, loot.md 4.1) and GLMs still run. Decide
   per mod whether to keep them (they're on top of the tree's loot).

### Decisions
- **Tree layout** (the row's open decision): recommend `creativeengineering:loot/container/<setting>/<role>/<tier>`
  with setting in {village, ocean, underground, nether, end, ruin, camp}, role = profession or room, tier in
  {mediocre, treasure}; categories under `container/basic/*`.
- **Keep mod-specific loot** (Philip's Ruins relics, YUNG's flavour): recommend a leaf may reference the mod's own
  table as one pool ("reuse existing tables").
- **JSON vs JS for the tree:** JSON + dict keys (recommend; editable, generator can draft it).

### Gotchas
- `remap` on a vanilla table drops goldenfood's / other overrides anyway; keep `useVanilla` + `restoreInjection`
  ordering in mind (remap should run after them, or replace them for remapped tables).
- Wares agreement / package tables are item contents rolled in code: never remap (`packExclude` list).
- Tables a structure container names but nobody ships (aliases, finding 5) can be mapped straight to a node.

### Tests
- **LT-36 Tree:** `/loottuning` lists N nodes defined and M tables remapped; `/dumploot` shows a remapped village
  table as one `loot_table` pool; 30 rolls give items from its node's categories.
