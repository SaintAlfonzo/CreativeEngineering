# axe-tag-ghost-entries

> minecraft:mineable/axe was silently dropped by vanilla because Create D&D's tag file lists 7 unregistered creative_* blocks; fixed in blocktags.js; also the D&D Jetpack tooltip NPE that killed client TagsUpdatedEvent and caused the first-inventory-open JEI freeze (fixed via Creative Common)

Moved from agent memory 2026-11-16 (last edited there 2026-09-27). Repo status docs win over any status line here.

Found 2026-09-26: axes did nothing (wood at fist speed, WTHIT "no valid tool") in SP **and** MP, since at least 9-25. Cause: `Create-DnDesire-1.19.2-1.2c.Beta Mid-Dev.jar` ships `data/minecraft/tags/blocks/mineable/axe.json` naming `create_dd:creative_{encased_shaft,encased_cogwheel,encased_large_cogwheel,encased_fluid_pipe,depot,mixer,press}`, which the jar never registers. One missing required entry makes vanilla drop the WHOLE merged tag, so it isn't even listed in a /dumptags dump. Fix: `t.remove(e, 'minecraft:mineable/axe', [...])` at the top of `kubejs/server_scripts/tags/blocktags.js`. This works because KubeJS's TagLoaderMixin runs at `TagLoader.load` RETURN, before vanilla resolves entries, and ID-filter remove doesn't check the registry.

**How to spot the next one:** the log line `Couldn't load tag [entries...] as it is missing following references` prints the ENTRY list, not the tag id. Grep the jars for one listed entry to find which tag file it is. Still broken the same way, but harmless for gameplay: the `#minecraft:village` structure tag (themissingvillages ghost structures, cascades into supplementaries/pneumaticcraft/monobank structure tags), `creategoggles:modifier/goggle_incompatible` (mekanism), and `rusticdelight:cherry_blossom_ingredients` (1.20 cherry blocks).

**Related client bug, FIXED 2026-09-26 (built):** D&D `JetpackItem.appendHoverText` (`m_7373_`) NPEs on `level.isClientSide()` with a null level while the creative search tree is built inside `ClientPacketListener.handleUpdateTags`, on every login and `/reload`, in singleplayer too. That aborts the rest of the handler, so the client `TagsUpdatedEvent` never fires. JEI then starts synchronously on the first screen open ("A Screen is opening but JEI hasn't started yet" then "Starting JEI took 6-18 s"), which is the **first-E-press lag spike**, and KubeJS spams "Tags have not been bound". It was the only "Error executing task on Client" cause in 2 days of logs. Fix: Creative Common client mixin `JetpackItemTooltipMixin` (@Redirect `Level.m_5776_` makes null false). Verify: after join the log should show JEI StartEventObserver receiving TagsUpdatedEvent and "Starting JEI took" BEFORE any screen opens.
